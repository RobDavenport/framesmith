One lab. Clear ownership.
Change the rules. See exactly why a combo works. Take the combat data into your game.
  • Timing, links, frame data: experiment 1, actual hitstun continuity, both timelines and the searchable frame table.
  • Cancels, frame windows, conditions, denies and tags: experiments 2 and 4. The runtime helper decides; the graph shows authored rules.
  • Named resources, caps, requirements and atomic costs: experiment 3. Energy and ammo are separate pools. The host applies authored gains on real events.
  • Collision: experiment 5 queries FSPK hit/hurt/push rectangles. Change spacing or authored reach; see hit, block or whiff. The fighter uses AABBs. Separate circle/circle, capsule/capsule and AABB/circle helper probes expose their exact caller inputs; other pairings are not claimed.
  • Events, notifies, custom properties and advanced hit data: experiment 6 and Twin Pulse. Data requests the spark/sound; this host draws/plays it and applies per-hit stats, stun and hitstop.
  • Globals, per-character overrides and inheritance: experiment 7 and the source inspector. Shared idle is included with an override; Charged Arc is resolved from Arc, not a copied move. Full variant-overlay GUI editing is not claimed.
  • Rules and validation: experiment 8 rejects a genuinely invalid draft and keeps the last good pack. Browser and CLI compile the same Rust source.
  • Training: guard policies, input history, slow motion, single-frame forward/back, full checkpoint/restore and per-frame replay. Four manual combo trials use the same simulation.
  • Data handoff: live source → validator → FSPK v2 → runtime; download the actual current pack or editable project and reload the pack. The FSPK payload retains rich typed data. JSON is authoring data, not the combat engine.
  • Editor/integration surfaces: the downloaded project belongs in the existing editor, CLI or MCP workflow. Sprite/GLTF preview, the desktop bulk editor and MCP transport are not embedded in this page.
Not a complete engine: movement/knockback, entities, effects, animation assets and custom game policy remain the consuming game's responsibility. This stationary lab handles only its named demonstration behaviors. It doesn't pretend every preserved field executes automatically.
60 Hz, input buffering, presentation, damage/stun policy and a 60-second recording limit belong to this demo—not FrameSmith's core. Human judgment still decides whether the tool feels good.
